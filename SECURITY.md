# Security policy

## Reporting a vulnerability

Report privately through
[GitHub's advisory form](https://github.com/ngsanogo/yagit/security/advisories/new).
Never in a public issue.

Please include what an attacker gains, and the smallest sequence that
demonstrates it. Expect a first reply within a week.

## Incident response

There is one maintainer. A report, or a finding from CodeQL, Dependabot or
Scorecard, is handled in this order:

1. **Triage.** What does an attacker gain, and is it already being exploited?
2. **Severity.** Does it reach repositories the user opened, the session
   token, or only a local development convenience?
3. **Fix.** Patch on a private fork, through GitHub's advisory workflow. Do
   not open a public pull request until the advisory is ready to publish.
4. **Disclose.** Publish the advisory with the fix, and mention it in the
   release notes of the version that carries it.

There is no separate security mailing list and no second person to escalate
to inside the project.

## Supported versions

yagit is pre-1.0 and under active development. Only `main` is supported; there
is nothing to backport to yet.

## What yagit is, in security terms

yagit is a local daemon with **read and write access to every git repository
you open with it**. It runs as you, with your credentials. Treat its session
token the way you would treat a shell on your own machine.

Two properties matter more than any other, and both are enforced in code:

**The daemon listens on the loopback by default.** The built binary binds
`127.0.0.1:7420`, and only `-addr` (or `YAGIT_ADDR`) moves it — the binary
never reads `.env`. In development `./do` derives that address from
`YAGIT_PUBLIC_HOST` in `.env`: a loopback name keeps the daemon on the
loopback; a non-loopback name widens it to `0.0.0.0` only when
`YAGIT_LISTEN_ALL=1` is also set. Widening is meant for reaching a headless
development machine from your own browser, not for putting yagit on a network
you do not control. There is no authentication beyond the session token; do not
expose the daemon to an untrusted network without TLS.

**Every route requires the session token**, exchanged for an HttpOnly cookie
via `POST /api/session` rather than embedded in the startup URL. It is 256 bits
of entropy, generated by the daemon at startup — or, under `./do`, minted once
into `.yagit/session-token` and handed over through the `YAGIT_TOKEN`
environment variable rather than a command-line flag, which `ps` would show to
every user on the machine. That file is the checkout's, not the run's: `./do`
reuses it across restarts. `./do up --new-token` replaces it, and ends every
session holding the old one
([ADR 0026](docs/adr/0026-the-session-token-outlives-the-run.md)). It is the
only token file: whether a daemon is running is asked of the port, never of a
file the daemon left behind
([ADR 0027](docs/adr/0027-the-stack-is-asked-not-a-file.md)).

The rest of the model follows from those two:

- **A repository is opened by path, then addressed by opaque id.** The only
  place a client-supplied path is accepted is the open call, which resolves
  symlinks and rejects anything outside `YAGIT_ROOT`. Afterwards the client
  only ever names ids, so a hostile page cannot designate a file.
- **The one route that writes a file works through an `os.Root` on the work
  tree.** `PUT /api/repos/{id}/file` is the only place the daemon writes a file
  directly rather than through git ([ADR
  0017](docs/adr/0017-yagit-edits-files.md)). It builds no absolute path at
  all: the kernel walks each component and refuses one that leaves the work
  tree, which a check followed by an open cannot promise — a symlink swapped
  between the two beats it. Anything under a git directory is refused outright,
  and so is a `.git` at any depth, directory or the one-line pointer file a
  linked worktree uses: `.git/config` names programs git runs (`core.pager`,
  `core.fsmonitor`) and the pointer names where git reads its state from, so
  writing either is arbitrary execution on the next command. A save is also
  refused unless it carries the fingerprint of the content it started from, so
  a stale buffer cannot overwrite work that arrived in between.
- **Cookie-authenticated mutating requests must carry a known `Origin`.** A
  request that presents the token explicitly — header or query string — proves
  it knows the secret and needs no origin check; a cookie is attached by the
  browser on its own, and is the only case a third-party site could trigger.
  The session cookie is `HttpOnly` and `SameSite=Strict`. Every HTTP response
  carries baseline security headers (CSP, `X-Frame-Options`, `Referrer-Policy`,
  and others).
- **Presenting a credential is rate limited; using one is not.** Six hundred
  attempts a minute per client address, counted on `POST /api/session` and on
  every request that arrives without a valid token — the same act either way.
  Requests that carry the token are not counted: reaching those routes means
  holding the secret, and the daemon binds the loopback, where every
  legitimate client and any local process share one address. A budget they
  share throttles the user and not the probe. The bound is there so a runaway
  loop cannot occupy the daemon; it is not what makes the token hard to guess.
  256 bits is.
- **git is never invoked through a shell.** Arguments are always passed as an
  array, so a branch name containing `;` can trigger nothing.

  One string does reach a shell, and it is git's own doing rather than an
  exception to the rule: `GIT_SEQUENCE_EDITOR`, which an interactive rebase
  sets so that git can obtain its todo list, is defined by git as a shell
  command and appended to by git without quoting. yagit quotes its own parts —
  its executable path and a temporary file's — so an installation path
  containing a space or a quote stays one word. Nothing user-supplied appears
  in it: the plan itself travels as a file, and its contents are object names
  and verbs the daemon checked against the repository
  ([ADR 0029](docs/adr/0029-a-rebase-plan-is-written-not-edited.md)).
- **The daemon builds git's environment from an allowlist** rather than
  inheriting yours, so a stray `GIT_DIR` or `GIT_SSH_COMMAND` has no effect. It
  pins four settings (`LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`,
  `GIT_PAGER=cat`) and passes through `PATH`, `HOME`, and — when they are already
  set — `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`. `HOME` is deliberate:
  yagit runs *your* git, with your configuration, so whatever your gitconfig
  already does to git in your terminal it also does here.

## Verifying a release

Every binary published by the release workflow carries a Sigstore-signed
provenance attestation: what was built, from which commit, by which workflow
run. Check it before running one:

```sh
gh attestation verify yagit-linux-amd64 --repo ngsanogo/yagit
```

`SHA256SUMS` is published alongside, but the two answer different questions. A
checksum says the bytes did not change in transit; it says nothing about where
they came from, and it is served by whoever served the binaries — an attacker
able to replace one can replace the other. The attestation is signed by a
certificate that existed only for the length of that workflow run and cannot be
reissued, so it holds even if this repository does not.

An SPDX bill of materials is attached too. The Go side is one direct dependency
deep — fsnotify, and the `golang.org/x/sys` it brings with it — so a naive
reading says an inventory here is two lines. It is not: `./do build` embeds the
built frontend into every binary, and that frontend is compiled from several
hundred npm packages which ship inside the executable.

## Repository protections

These are what this repository is set up to run. Enable the GitHub-side toggles
on the repository settings page when the project is published; the workflows
live in `.github/workflows/`.

- Private vulnerability reporting (the form above).
- Secret scanning and push protection.
- CodeQL on Go and the frontend, `security-extended` query set, on every
  pull request and weekly on `main` (`.github/workflows/codeql.yml`).
- Dependabot on npm, Go modules and GitHub Actions, with a seven-day
  cooldown. `./do audit` is the same check a contributor runs, and covers
  the Go standard library which Dependabot does not.
- OpenSSF Scorecard, publishing results to the repository Security tab
  (`.github/workflows/supply-chain.yml`).

## Design consequences

These follow from the model above. They are listed so nobody has to rediscover
them:

- **Plain HTTP by default.** yagit serves plain HTTP unless both
  `YAGIT_TLS_CERT` and `YAGIT_TLS_KEY` are set (or `-tls-cert` / `-tls-key`).
  On plain HTTP the session cookie omits the `Secure` attribute on purpose: a
  browser never sends a Secure cookie over `http://`, so setting it would not
  harden the session, it would end it. Use TLS when the daemon is reachable
  beyond the loopback.
- **Network exposure is explicit.** Binding to a non-loopback address or
  listening on `0.0.0.0` requires `-listen-all` or `YAGIT_LISTEN_ALL=1`.
  `./do` widens the listen address only when both a non-loopback
  `YAGIT_PUBLIC_HOST` and `YAGIT_LISTEN_ALL=1` are set.
- **The token grants everything.** There are no scopes and no per-repository
  permissions. Anyone who reads `.yagit/session-token`, or the process
  environment of a stack `./do` started, has the same access you do.
- **The token does not rotate on its own.** Under `./do` it lives as long as
  the checkout. A token that leaked into a screenshot or a pasted log stays
  valid until somebody rotates it. `./do up --new-token` stops the running
  stack, replaces the file, and starts the stack on the new token, so the old
  one is refused from that moment. Deleting `.yagit/session-token` by hand
  revokes nothing until the next `./do up`, which mints a replacement and
  restarts a stack that refuses it. A released binary is unaffected: it
  generates a token per start and writes one only when asked to.
- **The token does not belong in an API URL, and cannot be put there.** The
  announced address is printed without `?token=`. A browser exchanges the token
  through `POST /api/session`, or through the form the unauthorized page
  serves, and gets the HttpOnly cookie. `?token=` is accepted on `GET /` alone
  — for a tool whose only move is to open a URL — and is swapped for the cookie
  and stripped from the address before the page loads. Every route under
  `/api/` takes the `X-Yagit-Token` header, so the secret never reaches browser
  history, a `Referer`, or a proxy log.
- **Anyone with your user account has that access already**, so the token is
  not a boundary against a local attacker who is already you. `.yagit/` is
  locked down for that reason: it holds the token and the throwaway stack's
  log — every git command the daemon ran and the path of every repository it
  touched. On Unix that is mode `0700` / `0600`; on Windows an explicit
  owner-only ACL. See
  [ADR 0035](docs/adr/0035-secrets-get-an-owner-only-acl-on-windows.md).
- **On a multi-user host the loopback is shared.** `127.0.0.1:7420` is one
  port for every account on the machine. `./do` asks that port whether a stack
  is up: first without a credential, which a yagit daemon refuses and a
  stranger answers — the stored token is never sent to something that answers
  — and then with it, so `./do` can tell its own stack from a daemon holding
  another token. A process running as you could read `.yagit/session-token`
  anyway, so the case that matters is another account: one that binds the port
  while your stack is down, refuses the bare request, and then accepts any
  token, sees the secret on that second probe. Do not run yagit on a shared
  host you do not trust, and use `./do up --new-token` if the token may have
  been exposed.
